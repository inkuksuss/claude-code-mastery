## 1. 개요

### 1.1 문제 정의

소규모 사업자·프리랜서는 견적서를 엑셀/워드로 만들어 PDF로 변환한 뒤 이메일·메신저로 전달한다. 이 과정에서 다음 문제가 발생한다.

- 견적서 수정 시마다 파일을 다시 만들어 재전송해야 하며, 클라이언트가 구버전을 보는 사고가 잦다
- 견적서 데이터가 파일 단위로 흩어져 이력 관리·검색이 불가능하다
- 별도 견적 관리 SaaS는 학습 비용과 월 구독료 부담이 있다

본 제품은 **공급자가 이미 쓰고 있는 노션을 어드민으로 그대로 사용**하고, 클라이언트에게는 **항상 최신 내용이 반영되는 웹 링크 + PDF 다운로드**를 제공하여 이 문제를 해결한다.

### 1.2 타깃 사용자 페르소나

**공급자 — 김프리 (34세, 프리랜서 웹 개발자)**
- 월 3~5건의 견적서를 발행하며, 프로젝트 관리를 이미 노션으로 하고 있다
- 견적서 때문에 별도 툴에 가입하거나 어드민 화면을 배우고 싶지 않다
- 원하는 것: "노션에 한 줄 추가하면 클라이언트에게 보낼 링크가 나오는 것"

**클라이언트 — 박대표 (45세, 중소기업 대표)**
- IT 도구에 익숙하지 않으며, 회원가입이 필요한 서비스는 이탈한다
- 받은 견적서를 내부 결재용으로 PDF 파일로 보관해야 한다
- 원하는 것: "링크 클릭 한 번으로 견적서를 보고, 버튼 한 번으로 PDF 저장"

### 1.3 핵심 가치 제안

> **"노션에 입력하면 끝. 클라이언트는 링크로 보고 PDF로 받는다."**

- 공급자: 어드민 개발/학습 비용 0 — 노션 Database가 곧 관리 화면
- 클라이언트: 회원가입 없이 링크 하나로 열람, 항상 최신 버전 보장, PDF 보관 가능

## 2. 가정 (Assumptions)

질문 단계에서 확정된 사항 외에, 아래 항목은 합리적 기본값으로 가정한다. 구현 전 변경 가능하다.

| # | 가정 | 근거 |
| --- | --- | --- |
| A1 | 공급자는 **단일 사업자(싱글 테넌트)** 다. 여러 공급자를 위한 멀티 테넌시는 고려하지 않는다 | MVP 검증 대상은 1인 공급자 시나리오 |
| A2 | 견적서 1건 = Notion Database의 **페이지 1개**, 견적 항목(품목)은 해당 페이지 안의 **인라인 테이블(자식 Database)** 로 관리한다 | 노션 UX상 가장 자연스러운 구조 |
| A3 | 공유 토큰은 공급자가 만들지 않고, **Notion 자동화 또는 수동으로 UUID를 속성에 입력**한다 (토큰 발급 UI는 MVP 범위 외) | 발급 UI를 만들면 어드민이 생겨 MVP 원칙에 어긋남 |
| A4 | 부가세는 **10% 단일 세율**로 자동 계산하며, 면세 항목은 지원하지 않는다 | 국내 일반 용역 견적 기준 |
| A5 | PDF 레이아웃은 **A4 세로 1종**만 제공하며 커스텀 템플릿은 지원하지 않는다 | 서식 요구가 확정되지 않아 표준 견적서 양식으로 고정 |
| A6 | 견적서 열람 트래픽은 **일 100회 미만**으로 가정한다 (Notion API rate limit 산정 기준) | 페르소나 기준 월 발행량 3~5건 |
| A7 | 공급자 정보(상호, 대표자, 연락처, 로고 등)는 **환경 변수 또는 정적 설정 파일**로 관리한다 | 싱글 테넌트이므로 DB화 불필요 |

**확정된 사항 (질문 단계 답변):**
- 접근 제어: **토큰 링크만** (비밀번호·만료일 없음)
- PDF 생성: **서버 생성** (Route Handler)
- 상태 흐름: **3단계** — 작성중 → 발송됨 → 승인/만료
- 통화·언어: **KRW · 한국어만**

## 3. 사용자 스토리

### 공급자 (김프리)

- **S1.** 공급자로서, 노션 Database에 견적서 내용을 입력하고 싶다. 그래서 별도 어드민 없이 익숙한 도구로 견적서를 관리할 수 있다.
- **S2.** 공급자로서, 견적서 상태를 '발송됨'으로 바꾸면 웹 링크가 활성화되길 원한다. 그래서 작성 중인 미완성 견적서가 클라이언트에게 노출되는 사고를 막을 수 있다.
- **S3.** 공급자로서, 노션에서 금액·항목을 수정하면 웹 페이지에 자동 반영되길 원한다. 그래서 수정본을 다시 보낼 필요 없이 같은 링크를 유지할 수 있다.
- **S4.** 공급자로서, 유효기간이 지난 견적서는 '만료' 상태로 표시되길 원한다. 그래서 옛 가격으로 계약이 진행되는 위험을 줄일 수 있다.

### 클라이언트 (박대표)

- **C1.** 클라이언트로서, 받은 링크를 클릭하면 회원가입 없이 바로 견적서를 보고 싶다. 그래서 절차 없이 내용을 확인할 수 있다.
- **C2.** 클라이언트로서, 견적서를 PDF로 다운로드하고 싶다. 그래서 내부 결재·보관용 파일로 사용할 수 있다.
- **C3.** 클라이언트로서, 휴대폰에서도 견적서를 깨짐 없이 보고 싶다. 그래서 이동 중에도 내용을 검토할 수 있다.
- **C4.** 클라이언트로서, 견적서의 상태(발송됨/승인/만료)를 페이지에서 확인하고 싶다. 그래서 이 견적이 아직 유효한지 판단할 수 있다.

## 5. 기능 요구사항

### 5.1 Notion 데이터 스키마 (P0)

**견적서 Database (`Quotes`)** — 페이지 1개 = 견적서 1건

| 속성명 | Notion 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| 견적명 | Title | ✅ | 예: "쇼핑몰 리뉴얼 견적" |
| 견적번호 | Rich text | ✅ | 예: `Q-2026-001` (PDF 파일명에 사용) |
| 공유토큰 | Rich text | ✅ | UUID v4. URL 경로에 사용 |
| 상태 | Select | ✅ | `작성중` / `발송됨` / `승인` / `만료` |
| 클라이언트명 | Rich text | ✅ | 예: "(주)박대표컴퍼니" |
| 담당자 | Rich text | — | 클라이언트 측 담당자명 |
| 발행일 | Date | ✅ | 견적서 발행일 |
| 유효기간 | Date | ✅ | 이 날짜 경과 시 자동 만료 처리 |
| 비고 | Rich text | — | 특약·안내 문구 (여러 줄) |

**견적 항목 Database (`QuoteItems`)** — 견적서 페이지 내 인라인 자식 Database (가정 A2)

| 속성명 | Notion 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| 항목명 | Title | ✅ | 예: "메인 페이지 디자인" |
| 수량 | Number | ✅ | 기본 1 |
| 단가 | Number (원) | ✅ | 원화 정수 |
| 합계 | Formula | ✅ | `수량 × 단가` |
| 순서 | Number | — | 웹/PDF 표시 정렬 기준 (미입력 시 생성순) |

**금액 계산 규칙** (웹 서버에서 계산, Notion Formula는 표시 보조용):
- 공급가액 = Σ(수량 × 단가)
- 부가세 = 공급가액 × 10% (원 단위 반올림, 가정 A4)
- 총액 = 공급가액 + 부가세

**인수 조건**
- [ ] 위 스키마대로 Notion Database를 만들고 샘플 견적서 1건(항목 3개 이상)을 입력하면 웹에서 조회된다
- [ ] `합계`·부가세·총액이 웹/PDF에서 서버 계산값으로 일치하게 표시된다
- [ ] 필수 속성이 비어 있는 견적서는 웹에서 "견적서 정보가 올바르지 않습니다" 오류 화면을 표시한다 (500이 아닌 안내 화면)

### 5.2 견적서 웹 뷰 페이지 (P0)

**URL 구조:** `GET /quote/[token]` — `token`은 공유토큰 속성값(UUID)

**표시 항목 (위에서 아래 순):**
1. 공급자 정보 블록 — 상호·대표자·연락처·이메일 (환경 변수 기반, 가정 A7)
2. 견적서 헤더 — 견적명, 견적번호, 발행일, 유효기간, 상태 배지
3. 수신자 블록 — 클라이언트명, 담당자
4. 견적 항목 테이블 — 항목명 / 수량 / 단가 / 합계 (순서 속성 오름차순)
5. 금액 요약 — 공급가액 / 부가세(10%) / **총액** (총액 강조)
6. 비고
7. PDF 다운로드 버튼 (우측 상단 고정 또는 하단)

**상태별 노출 규칙:**

| 상태 | 웹 열람 | 표시 |
| --- | --- | --- |
| 작성중 | ❌ 404 | — |
| 발송됨 | ✅ | 상태 배지 "발송됨" |
| 승인 | ✅ | 상태 배지 "승인" |
| 만료 | ✅ | 상태 배지 "만료" + 상단 만료 안내 배너 |
| (유효기간 경과) | ✅ | 상태값과 무관하게 '만료'로 취급 (P1) |

**인수 조건**
- [ ] 유효한 토큰 + '발송됨' 이상 상태의 견적서 URL 접속 시 위 7개 블록이 모두 렌더링된다
- [ ] 금액은 `1,234,567원` 형식(천 단위 콤마)으로 표시된다
- [ ] '작성중' 상태 견적서의 토큰으로 접속 시 404 페이지가 표시된다
- [ ] 375px(모바일) 뷰포트에서 가로 스크롤 없이 견적 항목 테이블이 표시된다 (테이블 자체는 내부 스크롤 허용)
- [ ] 페이지는 서버 컴포넌트로 렌더링되며, `'use client'`는 PDF 다운로드 버튼 등 상호작용 요소에만 사용된다

### 5.3 접근 제어 (P0)

- 토큰은 **UUID v4 (122비트 엔트로피)** 로 추측 불가능해야 한다
- 존재하지 않는 토큰, '작성중' 상태, 빈 토큰 → 모두 **동일한 404 응답** (존재 여부를 구분할 수 없어야 함)
- 견적서 페이지는 검색엔진에 노출되지 않도록 `robots` 메타 `noindex, nofollow`를 설정한다
- Notion API 키는 서버 환경 변수로만 사용하며 클라이언트 번들에 포함되지 않는다

**인수 조건**
- [ ] 무작위 UUID로 접속 시 404가 표시되고, 응답 본문·상태코드가 '작성중' 견적서 접속과 동일하다
- [ ] 페이지 응답 HTML에 `noindex` 메타 태그가 포함된다
- [ ] 클라이언트 번들(브라우저 개발자 도구)에서 `NOTION_API_KEY` 문자열이 검색되지 않는다

### 5.4 PDF 다운로드 (P0)

**생성 방식:** 서버 생성 — `GET /quote/[token]/pdf` Route Handler에서 PDF 바이너리 응답

- **파일명 규칙:** `견적서_{견적번호}_{클라이언트명}.pdf` (예: `견적서_Q-2026-001_박대표컴퍼니.pdf`) — `Content-Disposition: attachment` 헤더로 지정
- **레이아웃:** A4 세로 1종 (가정 A5). 웹 뷰와 동일한 7개 블록 구성. 항목이 많아 1페이지를 넘으면 테이블이 다음 페이지로 이어지고 페이지 번호를 표시한다
- **한글 폰트:** Pretendard(또는 Noto Sans KR) 서브셋 폰트 파일을 저장소에 포함해 PDF에 임베딩한다. 시스템 폰트에 의존하지 않는다
- **접근 제어:** 웹 뷰와 동일 — '작성중'/토큰 불일치 시 404

**인수 조건**
- [ ] PDF 다운로드 버튼 클릭 시 위 규칙의 파일명으로 다운로드된다
- [ ] 생성된 PDF에서 한글이 깨지지 않는다 (macOS 미리보기·Windows Acrobat 기준)
- [ ] 견적 항목 30개 입력 시 2페이지 이상으로 자연스럽게 분할되고 페이지 번호가 표시된다
- [ ] PDF의 금액 합계가 웹 뷰와 일치한다
- [ ] '작성중' 견적서의 PDF URL 직접 호출 시 404가 반환된다

## 6. 비기능 요구사항

### 6.1 성능

- **캐싱 전략:** 견적서 페이지는 요청 시 렌더링하되 **60초 revalidate 캐싱** 적용 (Notion 수정 → 최대 60초 내 반영). Notion SDK 호출은 `unstable_cache`(또는 `"use cache"`) + `revalidate: 60`으로 감싼다
- 캐시 히트 시 페이지 응답 TTFB 1초 이내, 캐시 미스 시 3초 이내 (Notion API 왕복 포함)
- PDF 생성 응답은 10초 이내 (항목 30개 기준)
- Notion API rate limit(평균 3 req/s)은 가정 A6(일 100회 열람) + 캐싱으로 여유 확보

### 6.2 UI/호환성

- 모바일(375px)~데스크톱(1280px+) 반응형
- 다크 모드: 웹 뷰는 next-themes 기반 라이트/다크 대응 (P1). **PDF는 항상 라이트 테마로 고정**
- 브라우저: 최신 Chrome / Safari / Edge, iOS Safari

### 6.3 접근성 (최소 기준)

- 견적 항목은 시맨틱 `<table>`(caption 포함)로 마크업한다
- 상태 배지는 색상 외에 텍스트로도 상태를 전달한다
- 본문 텍스트 대비 4.5:1 이상, PDF 다운로드 버튼은 키보드로 조작 가능

## 7. 기술 고려사항

### 7.1 아키텍처 개요

```
[Notion Database] ← Notion API → [Next.js 서버]
                                    ├─ RSC: /quote/[token]/page.tsx  (웹 뷰, 60s 캐시)
                                    └─ Route Handler: /quote/[token]/pdf/route.ts  (PDF 생성)
                                          ↓
                                   [클라이언트 브라우저]
```

- 데이터 페칭은 **서버 컴포넌트에서 직접 수행** (RSC 기본 원칙). 클라이언트 fetch 없음
- 견적서 조회 로직은 `src/lib/notion.ts`에 모아 웹 뷰·PDF Route Handler가 공유한다
- Notion 응답 → 내부 타입 변환 시 **zod 스키마로 검증**하여 필수 속성 누락을 안내 화면으로 연결한다 (5.1 인수 조건)
- 전역 상태 불필요 — 읽기 전용 페이지이므로 기존 컨벤션(전역 상태 라이브러리 없음) 유지

### 7.2 Notion API 연동

- SDK: `@notionhq/client` (공식 SDK, 신규 의존성)
- 조회 흐름: ① `Quotes` DB에서 `공유토큰 == token` 필터 쿼리 → ② 페이지 블록 children에서 자식 Database(QuoteItems) 탐색 → ③ 항목 쿼리 → ④ zod 파싱·금액 계산

**환경 변수 (`.env.local`, `.env.example` 제공):**

| 변수 | 설명 |
| --- | --- |
| `NOTION_API_KEY` | Notion 내부 통합(Integration) 시크릿 |
| `NOTION_QUOTES_DB_ID` | 견적서 Database ID |
| `SUPPLIER_NAME` / `SUPPLIER_CEO` / `SUPPLIER_PHONE` / `SUPPLIER_EMAIL` | 공급자 정보 (가정 A7) |

### 7.3 PDF 생성 라이브러리 비교 및 선정

| 후보 | 장점 | 단점 | 판정 |
| --- | --- | --- | --- |
| **@react-pdf/renderer** | React 컴포넌트로 레이아웃 작성(스택 일관성), 폰트 임베딩 API 내장, 서버 실행 가벼움 | 웹 CSS와 별개 스타일 체계 | ✅ **선정** |
| Playwright/Puppeteer (HTML→PDF) | 웹 뷰 그대로 인쇄 → 디자인 재사용 | 브라우저 바이너리로 배포 무겁고 콜드스타트 큼, MVP 과잉 | ❌ |
| pdfkit / pdfmake | 경량 | 명령형/JSON 선언식이라 레이아웃 생산성 낮음, React 스택과 이질적 | ❌ |

**선정 근거:** 서버 생성(확정 사항) + 한글 폰트 임베딩 필수 + 이 프로젝트가 React/TS 스택이므로, 레이아웃을 React로 선언하고 폰트 등록이 간단한 `@react-pdf/renderer`가 총비용이 가장 낮다.

**신규 의존성 요약:** `@notionhq/client`, `@react-pdf/renderer`, Pretendard 서브셋 폰트 파일(에셋)

### 7.4 라우트/컴포넌트 구조 초안

```
src/
├── app/
│   └── quote/
│       └── [token]/
│           ├── page.tsx              # 견적서 웹 뷰 (RSC)
│           ├── not-found.tsx         # 토큰 불일치/작성중 안내
│           └── pdf/
│               └── route.ts          # PDF 생성 Route Handler
├── components/
│   └── quote/
│       ├── quote-header.tsx          # 견적명·번호·상태 배지
│       ├── quote-party-info.tsx      # 공급자/수신자 정보
│       ├── quote-items-table.tsx     # 견적 항목 테이블
│       ├── quote-summary.tsx         # 공급가액/부가세/총액
│       ├── quote-pdf-button.tsx      # 'use client' — 다운로드 버튼
│       └── quote-pdf-document.tsx    # @react-pdf/renderer 문서 정의
└── lib/
    ├── notion.ts                     # Notion 클라이언트·조회·캐싱
    ├── quote-schema.ts               # zod 스키마·내부 타입·금액 계산
    └── fonts/                        # PDF용 한글 폰트 에셋
```

- 파일명 kebab-case, named export, 들여쓰기 탭 등 기존 컨벤션 준수
- UI는 shadcn/ui 기존 컴포넌트(Badge, Table, Button 등) 우선 활용, 클래스 병합은 `cn()`

## 10. 리스크 및 대응

| # | 리스크 | 영향 | 완화 방안 |
| --- | --- | --- | --- |
| R1 | Notion API rate limit(평균 3 req/s) 초과 | 열람 실패 | 60초 revalidate 캐싱으로 견적서당 호출 최소화. 429 수신 시 재시도 1회 후 안내 화면 |
| R2 | PDF 한글 렌더링 깨짐/폰트 용량 | 산출물 품질 저하, 콜드스타트 증가 | 서브셋 폰트 사용(용량 절감), 1주차에 폰트 임베딩 스파이크 테스트를 먼저 수행 |

| R4 | 인라인 자식 Database 탐색의 API 복잡도(A2) | 1주차 지연 | 스파이크로 조기 검증. 어려울 경우 항목 Database를 별도 최상위 DB + Relation으로 전환 (스키마만 변경, 코드 영향 최소) |
| R5 | 토큰 유출 시 제3자 열람 | 정보 노출 | MVP는 링크 소지=열람 권한으로 정의(확정 사항). 유출 시 공급자가 노션에서 토큰 값을 교체하면 기존 링크 즉시 무효화됨을 가이드에 명시 |
