# PRD 작성 메타 프롬프트 — 노션 견적서 웹 뷰어 MVP

> 아래 프롬프트를 Claude Code에 그대로 입력하면 MVP PRD 문서를 생성합니다.
> 결과물은 `docs/PRD.md`로 저장하도록 지시되어 있습니다.

---

## 프롬프트

```markdown
# 역할

당신은 B2B SaaS 제품을 다수 출시해 본 시니어 프로덕트 매니저이자 테크니컬 라이터입니다.
개발자 1인이 2~4주 안에 구현 가능한 수준의 "실행 가능한 MVP PRD"를 작성하는 것이 임무입니다.

# 제품 컨텍스트

- 제품 한 줄 요약: 공급자가 **노션(Notion)에 견적서 내용을 입력**하면, 클라이언트가
  **전용 웹 페이지에서 견적서를 확인하고 PDF로 다운로드**할 수 있는 서비스
- 핵심 가치:
  - 공급자: 별도 어드민 없이 익숙한 노션을 그대로 견적서 관리 도구로 사용
  - 클라이언트: 회원가입 없이 공유 링크 하나로 견적서 열람 및 PDF 보관
- 데이터 소스: Notion API (견적서를 Notion Database로 관리한다고 가정)
- 산출물 형태: 반응형 웹 뷰 + PDF 다운로드

# 프로젝트 기술 제약 (PRD의 기술 고려사항 섹션에 반드시 반영)

이 PRD는 아래 기존 프로젝트 위에 구현됩니다. 기술 선택 시 이 스택을 벗어나지 마세요.

- Next.js 16.2 (App Router) + React 19 + TypeScript (strict)
- React Compiler 활성화 → useMemo/useCallback/React.memo 수동 최적화 금지
- Tailwind CSS v4 (CSS-first, tailwind.config 없음 — 테마는 src/app/globals.css)
- shadcn/ui (base-nova 스타일, Base UI 기반) + lucide-react + cva
- 폼: react-hook-form + zod(v4) + @hookform/resolvers
- 테마: next-themes / 유틸 훅: usehooks-ts
- 전역 상태 라이브러리 없음 (로컬 상태 + useLocalStorage)
- 서버 컴포넌트(RSC) 기본, 'use client'는 최소 사용
- UI 텍스트는 한국어
- 테스트 프레임워크 미설치 (테스트 계획을 PRD에 포함하지 말 것)
- 신규 의존성이 필요한 영역(예: Notion SDK, PDF 생성 라이브러리)은
  후보와 선택 근거를 PRD에 명시할 것

# 작성 절차 (반드시 순서대로)

1. **질문 단계**: PRD 작성 전, 요구사항 확정에 필요한 질문을 최대 5개까지 먼저 제시하라.
   (예: 견적서 필드 구성, 접근 제어 방식, PDF 서식 요구, 다국어/다중 통화 필요 여부,
   견적서 상태 흐름)
   - 사용자가 답하지 않은 항목은 합리적인 기본값을 스스로 가정하고,
     PRD의 "가정(Assumptions)" 섹션에 명시하라.
2. **PRD 작성 단계**: 아래 출력 구조에 따라 PRD를 작성하고 `docs/PRD.md`로 저장하라.

# PRD 출력 구조

아래 목차를 모두 포함한 한국어 마크다운 문서로 작성하라:

1. **개요**
   - 문제 정의, 타깃 사용자 페르소나(공급자/클라이언트 각 1개), 핵심 가치 제안
2. **가정 (Assumptions)**
   - 질문 단계에서 확정하지 못해 임의로 정한 사항 목록
3. **사용자 스토리**
   - "~로서 ~하고 싶다. 그래서 ~할 수 있다" 형식
   - 공급자 관점 3~5개, 클라이언트 관점 3~5개
4. **MVP 범위**
   - In Scope: 기능 목록 (각 기능에 우선순위 P0/P1 표기)
   - Out of Scope: 의도적으로 제외하는 것과 그 이유 (예: 전자서명, 결제, 이메일 알림, 회원 시스템)
5. **기능 요구사항** — 기능별로 상세히:
   - Notion 데이터 스키마: 견적서 Database 속성 정의
     (견적 번호, 클라이언트명, 항목/수량/단가/합계, 유효기간, 상태, 공유 토큰 등)
   - 견적서 웹 뷰 페이지: URL 구조(예: /quote/[token]), 표시 항목, 상태별 노출 규칙
   - 접근 제어: 추측 불가능한 공유 링크 토큰 방식 등 MVP 수준의 보안 정책
   - PDF 다운로드: 생성 방식(서버/클라이언트), 파일명 규칙, 레이아웃 요구사항, 한글 폰트 처리
   - 각 기능마다 **인수 조건(Acceptance Criteria)** 을 체크리스트로 명시
6. **비기능 요구사항**
   - 성능: Notion API 응답 캐싱 전략 (Next.js 캐싱/revalidate 활용)
   - 모바일 반응형, 다크 모드 대응, 접근성 최소 기준
7. **기술 고려사항**
   - 위 기술 제약 기반의 아키텍처 개요 (RSC 데이터 페칭 흐름, Route Handler 활용)
   - Notion API 연동 방식과 환경 변수 목록
   - PDF 생성 라이브러리 후보 비교 및 선정 근거
   - 라우트/컴포넌트 구조 초안 (`src/app/`, `src/components/` 기준)
8. **성공 지표 (Success Metrics)**
   - MVP 검증에 필요한 최소한의 정량/정성 지표 3개 이내
9. **마일스톤**
   - 2~4주 기준 주차별 개발 순서 (P0 우선)
10. **리스크 및 대응**
    - Notion API rate limit, PDF 한글 렌더링 등 예상 리스크와 완화 방안

# 품질 기준

- 개발자가 PRD만 읽고 바로 구현에 착수할 수 있을 만큼 구체적으로 작성하라
- 모호한 표현("적절히", "빠르게") 대신 측정 가능한 기준을 사용하라
- 기능 요구사항과 인수 조건은 구현 여부를 예/아니오로 판정할 수 있게 작성하라
- MVP 원칙을 지켜라: 2~4주 안에 불가능한 기능은 과감히 Out of Scope로 보내라
- 문서 전체를 한국어로 작성하라
```

## 사용 방법

1. Claude Code 세션에서 위 프롬프트 블록 전체를 복사해 입력합니다.
2. Claude가 먼저 최대 5개의 질문을 제시하면, 아는 범위에서 답변합니다.
   (답하지 않은 항목은 가정으로 처리되어 PRD에 명시됩니다.)
3. 생성된 PRD는 `docs/PRD.md`에 저장됩니다.
4. 검토 후 가정(Assumptions) 섹션을 실제 요구사항으로 확정하며 문서를 다듬습니다.
